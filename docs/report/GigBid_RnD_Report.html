GigBid — R&D design review

AI-4016 Assignment II · Talha Qamar · repository github.com/Talha-Qamar/Agentic-A2 · live https://gigbid-d3l2.onrender.com · every number below is read from evals/results/ when this PDF is built (scripts/build_report.py); file names are given in brackets.

1. Problem and constraints

A freelancer on a bidding marketplace spends most of the week on three things: reading job posts to decide which are worth Connects, writing a proposal that proves fit, and answering client replies quickly. Each is easy to automate badly: an agent that bids on everything burns Connects and reputation, one that writes fluent but unproven claims loses the client in the first call, and one that sends on its own breaks platform rules.

Never automated. Sending a proposal or a message, spending Connects, and accepting an interview. The marketplace MCP server refuses submit_proposal/send_message unless the request carries an HMAC approval token that only the API's approval endpoint mints after a human click (mcp_servers/marketplace/server.py, common/tokens.py). The LLM never sees or produces that token.

Budgets declared before measurement (agent/config.yaml → budgets.declared): p95 latency 25 s per job analysed and 60 s per proposal; cost USD 0.002 per job analysed and USD 0.01 per proposal (list prices of the open models we use). Per thread: at most 40 graph steps, 60K tokens and 2 critique revisions; beyond that the run stops in needs_attention instead of looping.

Data. Three synthetic personas (ML engineer, full-stack developer, data analyst), each with a CV PDF, case studies in three writing styles, 14–15 code repositories (three with no case study, two with almost empty READMEs), reviews and ~150 past proposals with a hidden outcome rule. 600 labelled dev jobs (12% scams, 10% with planted injected instructions) and a 198-post live stream for GigSim; market statistics and 1,500 historical posts come from the Kaggle Upwork postings dataset (ODC-By). Details and limitations: docs/DATA_CARD.md.

2. Architecture

Bid graph (LangGraph StateGraph, typed state with reducers; rendered from code in docs/bid_graph.svg): intake (load job through the marketplace port, injection screen) → parallel analyst ∥ risk ∥ matcher (Send fan-out, merged by reducers) → decide (deterministic rule over evidence-based scores, so a job post cannot argue its way to BID) → pricing (market stats + live Connects policy) → writer → verifier (removes unsupported claims) → critic (≤2 revisions) → compliance (policy pack) → preview (saves a marketplace draft, dry-run submit) → approval = interrupt() → submit with the preview's idempotency key. Failures after retries and model fallbacks go to dead_letter; exhausted step/token budgets to needs_attention. Conversation graph: intent → liaison (grounded reply, rate floor, calendar slots) → compliance → approval interrupt → send (+ interview hold).

Why each agent exists. Analyst: turns free text into a JobSpec (requirements, deliverables, budget) that every later node can rely on. Risk: scam and client-history signals must be scored independently of fit, otherwise a well-matched scam gets a bid. Matcher: maps every requirement to portfolio evidence through the Portfolio MCP server; this is the only source of the fit score. Writer/Verifier/Critic are split because a writer that also judges its own claims is the failure we were trying to remove; the verifier is not an LLM by default (cross-encoder support + number/entity checks, LLM judge only for borderline claims). Compliance is separate so that the same guard runs on human edits and client replies. Agents exchange Pydantic objects (agent/handoffs.py: JobSpec, RiskReport, FitReport, BidDecision, PriceQuote, ProposalDraft, Critique, ComplianceVerdict, ApprovalDecision).

Marketplace port and MCP surface. Agents never call GigSim. They call three MCP servers we wrote — Portfolio (published, uvx install), Marketplace (port with a GigSim adapter and an Upwork-MCP adapter behind the same tools, switched by MARKETPLACE_MODE), Workspace (calendar holds, email drafts) — over streamable HTTP with a per-user JWT and the trace id in a header. Each agent gets an allowlist of tool names; writes are dry_run by default, carry an idempotency key, and are rate-limited per user below GigSim's limit; every marketplace call is written to an append-only audit log (Postgres trigger). Twenty tools, one row each with annotations and auth: docs/TOOLS.md.

Stores. Postgres holds LangGraph checkpoints (approvals survive restarts: the graph resumes from the interrupt), app tables, pgvector chunks, the LangGraph memory store (style rules promoted only after an edit pattern recurs in ≥2 of the last 10 edits; outcome insights from GigSim results) and the audit log. Redis/Arq runs the worker (scout, analyse, resume, converse, pipeline sync). On the free hosting tier everything runs in one process (docs/adr/0004-deployment.md); docker compose runs the full multi-service stack with Phoenix tracing.

Degraded mode. If the marketplace server is down the API health check reports it, the UI shows a banner, scouting and sends are paused and queued, and analysis of saved jobs continues (apps/web/e2e/degraded.spec.ts).

3. R&D question A — does tool granularity change agent behaviour?

Hypothesis. A few task-shaped tools beat many fine-grained ones on selection accuracy and tokens, and rewriting descriptions from observed failures closes most of the remaining gap. Setup (evals/runners/tool_granularity.py): 40 portfolio tasks with a known correct call (evidence lookup, skill listing, outcome-filtered proposals, result lookup), one small open model in a ReAct loop, three Portfolio MCP servers that differ only in tool design: coarse (one match_requirements tool), by-type (six fine-grained search tools, one per document type) and rewritten (the default four tools with descriptions rewritten after reading the coarse and by-type failures). Metrics: tool-selection accuracy, argument accuracy, task success, tokens per task.

Negative result: reranking. The cross-encoder (ms-marco-MiniLM-L-6) lowered Recall@5 from 0.574 (V2) to 0.513 (V3) and added about two seconds at p95. Reading the misses: the reranker prefers chunks that paraphrase the requirement (past proposals, CV summary lines) over code and case-study results that prove it, which is exactly the evidence a proposal needs. A smaller embedding model (WordLlama, rag_benchmark_wordllama.json) kept the ranking of variants unchanged, so the conclusion is not an artefact of one embedder.

Claim verification. The verifier splits a draft into experience claims and checks each against the cited and re-retrieved evidence: cross-encoder support, every figure must appear in the evidence, every named entity too, LLM judge only for borderline cases. On the calibrated dev run, unsupported claims fell from 25% of claims to 0% before the critic saw the draft (12 claims, decision_eval.json).

Caveat. Gold evidence is defined through skills, which favours a skill-based retriever on explicitly named requirements; that is why recall on implied-skill jobs is reported separately, where V9 still leads.

Shipped choice: V9. Best Recall@5, MRR and nDCG@10 overall and on every persona and job type, p95 under 0.1 s, no model call at query time. End to end (B5):

6. The change request (GigSim policy 2026-11-02)

GigSim's policy changed mid-project: AI-drafted proposals must carry a disclosure line, the Connects price formula changed and a daily proposal cap was introduced. What we edited: data/policy_pack/rules.yaml (disclosure required + its text), infra/docker-compose.yml and render.yaml (policy version) — 3 files, 8 lines added, 4 removed, no Python changed (commit a783067, diff against 70c8062). Connects pricing and the daily cap were already read live through get_policy, and compliance already appended a disclosure line when the pack or the live policy asked for one. It took about ten minutes including the test run. Measured with the same code and the new GigSim policy, policy pack before vs after (change_request_before.json, change_request_after.json):

before (70c8062 rules) 9 1 - - 1 8

GigSim policy 2026-11-02 in both runs; commit a783067; profile open.

What it says about the design: rules that change with the platform live in data (policy pack, live policy), and the marketplace's own dry run is part of the graph, so a policy change shows up as a rejected preview, not as a rejected proposal.

7. Signature extension — X3 Portfolio builder

GitHub repository → README and code through the GitHub MCP server (get_file_contents) → LLM case study written from the repo text only → every claim verified against that repo's chunks (and named libraries against the code) → unsupported sentences deleted → saved into the user's portfolio, which the Portfolio server re-indexes incrementally. A second half mines skill gaps from skipped jobs and finds "hidden strengths" (skills present in code but in no prose) to say which case study to write next. Evaluation (portfolio_builder_eval.json): suggestions computed on the first half of the dev set, write-ups added, coverage and decisions re-measured on the held-out half.

portfolio_builder_eval.json pending

Result, stated plainly: the builder's drafts were grounded (no unsupported claim survived verification), but on the held-out jobs coverage, fit and bid decisions did not change. The suggested skills were rarely the deciding requirement in those jobs, and V9 already finds code-level evidence through the skill graph, so a prose write-up of the same project adds little for retrieval. Its value is for the human reader of the proposal (a citable result sentence instead of a code file), which this evaluation does not measure.

9. Safety and platform respect

Must never: send or spend without a human click; put contact details, external links or off-platform payment in a proposal; guarantee outcomes; follow instructions inside a job post or client message; leak one user's data to another; scrape or automate a browser against the real marketplace. Enforcement: approval tokens checked by the marketplace server, not the prompt; compliance guard (deterministic rules first, LLM second; an LLM-flagged block needs a concrete marker in the flagged text after the false positive in §8); untrusted text wrapped and screened, quarantined jobs skip the writer; per-user JWT scoping on every MCP server and tenant tests (scout_isolation.spec.ts); PII masked in logs and traces; live mode only through the official Upwork MCP with OAuth.
