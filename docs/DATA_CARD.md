# Data card

Everything GigBid evaluates on is either **real public data** (clearly attributed) or **synthetic data generated by
scripts in `data/generator/`** (deterministic seeds, labelled `synthetic: true` and banner-marked in every file).

## Real data

| Dataset | Use | Licence | Files |
|---|---|---|---|
| asaniczka, *Upwork Job Postings Dataset 2024 (50K Records)*, Kaggle | per-category hourly and fixed price percentiles (pricing, fair price bands); 1,500 historical job posts in GigSim | ODC Attribution License (ODC-By 1.0) | `gigsim/seed_data/market_stats.json`, `gigsim/seed_data/historical_jobs.jsonl` |

Source: https://www.kaggle.com/datasets/asaniczka/upwork-job-postings-dataset-2024-50k-records (53,058 rows; 52,4xx parsed).
Preprocessing (`data/generator/build_market.py`): category and skills parsed from the description field; hourly
midpoints (3-300 USD) and fixed budgets (5-100,000 USD) aggregated per category with >= 25 posts; 1,500 deduplicated
posts sampled from the personas' categories (seed 2026). The raw CSV is not committed; download it and run
`python data/generator/build_market.py <csv>`. Limitations: two weeks of 2024 postings; Upwork shows budgets only for
some posts; fixed budgets skew low (median ~$100-150), so price bands reflect what clients posted, not what freelancers earned.

## Synthetic data

| Artifact | Generator | Size |
|---|---|---|

### How the messiness is built in
* the same project appears as a case study, a README, CV bullets and in past proposals with different vocabulary
  (`Postgres`/`PostgreSQL`/`pg`), and some case studies replace a named tool with a description of the need;
* "implicit" skills appear only as imports in code files (e.g. Celery, tenacity) never in prose;
* 3 projects per persona have no case study; 2 repos per persona have READMEs that say almost nothing;
* job requirements are phrased explicitly (60%), implied (30%) or as vague wishes (10%).

### Labels (by construction)
* **Gold evidence**: a project is relevant to a requirement when its canonical skills (stack, implicit, tags)
  contain the requirement's skill; graded relevance = number of the job's requirements it covers. Skills present in
  more than 5 of a persona's 18 projects (e.g. Python, SQL) are excluded from requirements because they carry no fit signal.
* **Gold decision**: BID iff not a scam, requirement coverage >= 0.6 and the budget is at least 0.8 x the hourly
  floor (hourly) or 4 hours at the floor (fixed); otherwise SKIP.
* **Fair price band**: hourly [max(floor, category p25), max(target, category p75)] capped near the client's maximum;
  fixed [0.75 x budget_min, 1.05 x budget_max] (category percentiles from the real Kaggle data).
* **Past-proposal outcomes** follow a documented hidden rule (`build_personas.py::proposals`): specific openings,
  evidence relevant to the job and fair prices raise the reply probability; generic openings and padding lower it.

### Known biases and limitations
* Gold evidence is skill-based, so retrieval methods that use explicit skill names (V9 skill graph) are favoured on
  explicit requirements. We report recall separately for jobs with implied requirements (rag_ablation.json).
* Simulated clients use a transparent scoring rule (or an LLM in `GIGSIM_CLIENT_MODE=llm`), so GigSim outcomes
  measure agreement with that rule, not real client behaviour.
* Personas, clients and companies are invented; any resemblance to real businesses is accidental.
* The hidden test set is generated at run time from a seed kept outside the repo (`evals/runners/hidden_test.py`).
